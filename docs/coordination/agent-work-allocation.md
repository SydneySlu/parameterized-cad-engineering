# 轻量版首期 Agent 分工与依赖计划

状态：初步计划，尚未生成各 Agent 初始化 prompt，也尚未正式认领任务。

## 总体原则

项目采用“一个中枢、多个执行角色”的结构。Codex / ChatGPT 中枢维护任务依赖、接口契约、范围决策、阶段审查和最终合并；执行 Agent 可以并行工作，但不能自行改变零件族范围、Schema 语义、Typed CAD IR 语义或交付标准。所有 Agent 先读取 `AGENTS.md`、`docs/PROJECT_STATUS.md`、`docs/PROJECT_PLAN.md`、`docs/WORKLOG.md` 和 `docs/DECISIONS.md`。

轻量版的主链是：

```text
首期零件族冻结
        ↓
数据样本与参数 Schema
        ↓
Typed CAD IR v0 ──→ CadQuery/OCP 确定性构造器
        ↓                         ↓
LLM 结构化抽取与小样本检索 ──→ 验证器与有限修复循环
        ↓                         ↓
             集成评测与交付
```

其中数据和 LLM 可以在接口草案确定后并行，构造器和验证器必须围绕同一个 IR 版本实现。监督微调和强化学习不进入首期主线。

## 角色和边界

### 1. Codex / ChatGPT 中枢：规划、接口和审查

负责把用户目标拆成任务，冻结依赖和验收条件，维护 `PROJECT_STATUS`、`PROJECT_PLAN`、`TASKS`、`WORKLOG` 和 `DECISIONS`，生成后续 Agent prompt，审查 checkpoint 和 commit，并做最终集成判断。

Codex 作为 **Typed CAD IR 设计负责人**：定义 IR 的节点、参数、单位、依赖、约束、来源、错误码、版本和与 Schema 的映射；定义白名单 CadQuery 操作与构造器接口。Codex 不应把未验证的架构设想直接当成实现事实。

Codex 还负责跨模块审查：数据是否有来源和许可记录，LLM 是否只抽取显式信息，Schema 和 IR 是否一致，验证器是否能解释失败。重要结论可以交给另一个 Codex 对话框独立复核，但它只提供审查意见，不维护第二套状态。

### 2. 数据 Agent：数据获取、清洗和检索样本

可由 DSH 或专门的数据 Agent 承担。负责候选零件族的数据来源调查、许可/来源记录、CAD 或参数样本收集、去重、转换、渲染、质量抽查和 manifest。最终输出至少包括参数 JSON、Typed IR（如果已有）、渲染图、STEP 文件、验证结果、来源和版本字段。

数据 Agent 不负责擅自决定首期零件族、不修改 Schema 语义，也不把未经验证的网络 CAD 文件直接作为训练/评测真值。它可以提出“某类字段在公开数据中难以获得”的证据，供中枢和用户调整范围。

### 3. LLM Agent：结构化抽取、Prompt 和检索接入

负责云端/本地模型适配、Prompt、JSON 输出解析、示例注入、缺失字段追问和有限修复循环的实验。它与用户配合，重点验证不同模型在同一 Schema、同一测试集上的抽取质量和失败模式。

LLM Agent 只输出结构化意图/参数候选，不直接生成不受控的 CAD 代码，不绕过 Schema、Typed IR 和验证器。模型选择、Prompt 结果和检索收益必须记录模型版本、Prompt 版本、数据切分和评测条件。

### 4. Schema 与规则 Agent：结构校验和领域边界实现

由 CC 或熟悉 Python 校验库的编码 Agent 承担。负责 Pydantic/JSON Schema、单位归一化、字段来源、缺失字段、参数边界、接口约束、错误码和单元测试。该 Agent 根据已冻结的零件族和中枢确认的字段设计实现，不自行扩大零件族。

它是 LLM 与 IR 之间的第一道机器可检查接口，但不代替几何验证器：Schema 负责字段和参数关系，CAD 验证器负责实体有效性、拓扑/尺寸回读和零件族规则。

### 5. Typed CAD IR 计划 Agent：语义和接口设计

首选由 Codex 中枢承担，必要时另一个 Codex 对话框做独立设计复核。输出 IR v0 规范、示例、序列化格式、特征节点和引用规则、参数/约束表达、错误码、版本策略，以及从结构化参数到 IR 的映射。

它不直接把实现细节写成最终事实；任何会影响构造器、验证器或数据格式的改变，都要进入决策记录并通知相关 Agent。

### 6. CAD 执行 Agent：构造器和验证闭环实现

首选由 CC 承担。负责将冻结的 IR 编译为白名单 CadQuery/OCP 操作，生成 STEP 和可编辑构造记录，并实现实体有效性检查、STEP 回读、参数/接口规则验证、错误报告和有界修复接口。它应提供可重复运行的测试和示例。

CAD 执行 Agent 不改变 IR 的含义来迁就代码；发现 IR 无法表达需求时，先提交阻塞或变更建议，由 Codex 审查后更新 IR 版本。

### 7. 独立复核角色：按需启用

不是常驻的第七个开发 Agent。对高风险节点（零件族冻结、IR v0、验证指标、关键论文/数据结论）可以启动另一个 Codex 对话框，只做证据核对、反例检查和差异审查。复核结论回到当前中枢，由项目负责人决定是否采纳。

## 工作阶段和依赖

### 阶段 A：冻结范围和接口草案

负责人：Codex + 用户/导师。

先从三个候选零件族中冻结首期范围、支持/不支持项、单位体系和最小评测集。随后由 Codex 给出 Schema 与 IR 的接口草案。没有这一步，数据 Agent 可能收集到不可用的字段，LLM Agent 也无法做可比评测。

### 阶段 B：四条并行准备线

- 数据 Agent：调查来源并构造样本 manifest，先用草案字段，等 Schema 冻结后定版。
- LLM Agent：用少量人工样本验证 Prompt、结构化输出、缺失字段追问和检索示例注入。
- Schema/规则 Agent：实现字段校验、单位和参数边界，形成可供 LLM 与 IR 共用的校验接口。
- IR 计划 Agent：完成 IR v0 和编译器/验证器接口设计，接受数据与 Schema 的字段反馈。

这些线可以并行，但每条线都要在 checkpoint 标出“暂定字段”和“已冻结字段”，避免临时实验结果被误当成最终协议。

### 阶段 C：确定性 CAD 主链

Codex 审查 IR v0 后，CC 实现构造器、验证器和日志。验证器至少要能区分：结构字段错误、编译/执行错误、无效实体、STEP 回读错误、零件族规则失败和未知失败。先跑一个零件族的最小闭环，再扩展样本量。

### 阶段 D：集成评测和交付

由 Codex 统筹，LLM Agent 运行模型/Prompt 对照，数据 Agent 提供固定评测集，CC 修复接口和运行问题。统一比较无检索、带小样本检索、人工模板三种条件；记录字段准确率、追问正确率、CAD 执行成功率、几何/规则通过率、修复成功率、延迟和失败类型。

## 推荐的实际分配

| 工作线 | 主要负责人 | 配合者 | 首个可审查交付物 |
|---|---|---|---|
| 范围、依赖、接口和审查 | Codex 中枢 | 用户/导师、独立复核 Codex | 冻结决策、任务依赖、Schema/IR 接口草案 |
| 数据集与检索样本 | 数据 Agent（DSH 或专门 Agent） | Codex、Schema Agent、CC | 来源表、manifest v0、抽查报告 |
| LLM、Prompt、追问与检索注入 | LLM Agent | 用户、Codex、数据 Agent | 模型/Prompt 对照表和失败案例 |
| Schema 与规则校验 | CC（Schema/规则角色） | Codex、LLM Agent | Pydantic/JSON Schema、单位和规则测试 |
| Typed CAD IR 设计 | Codex 中枢 | 独立复核 Codex、CC | IR v0 规范、示例和错误码 |
| CAD 构造器与验证器实现 | CC（CAD 执行角色） | Codex、Schema Agent | 白名单构造器、STEP 回读、验证报告和测试 |
| 集成与验收 | Codex 中枢 | 全部 Agent、用户 | 固定评测结果、失败分类和交付记录 |

## 后续正式分派前需要确认的事项

1. 首期最终零件族和不支持项。
2. 数据 Agent、LLM Agent、Schema/规则 Agent 和 CC 的实际对话框/分支名称。
3. 是否把数据清洗与检索实现交给同一个 Agent；如果数据量增加，再拆成两个任务。
4. IR v0 是否先只覆盖一个零件族和有限特征集合。
5. 固定评测集规模、来源许可和验收阈值。
