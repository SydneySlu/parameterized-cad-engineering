# 项目记忆与交付工作手册

本手册把跨任务可复用的项目推进方法集中记录，避免对话压缩、Agent 更换或设备切换后丢失工作约定。仓库文档和 Git 历史仍是唯一事实源；本手册是执行索引，不取代 ADR、技术规范、任务 checkpoint 或交接审查协议。

## 1. 开始任务：先恢复事实，再行动

1. 确认当前仓库：`git rev-parse --show-toplevel`；只在共享项目 Git 根目录内工作。
2. 读取 `AGENTS.md`、`docs/PROJECT_STATUS.md`、`docs/PROJECT_PLAN.md`、`docs/WORKLOG.md`、`docs/DECISIONS.md`，以及相关任务 checkpoint/handoff 和最近的审查报告。
3. 检查 `git status --short --branch`、当前 HEAD、目标分支与相关提交；不要根据聊天记忆假定代码已合并、已 push 或文件仍未变。
4. 将本次请求映射到项目阶段、既有决策、上游/下游接口和明确禁止项。发现计划、架构或交付标准冲突时，先停在 `review`/`blocked`，必要时先增加 ADR，不以局部修补悄悄改变方向。
5. 把任务拆成最小可审查工作单元，说明输入、输出、负责人、验证方式、边界和退出条件。一次只处理一个已授权工作单元；独立后续工作不要顺手扩进来。

## 2. 角色和工作分配

- Codex 中枢负责总体路线、决策、任务收束、风险判断和独立验收；不应只复述执行者报告，必须查看共享文件、差异和实际验证证据。
- CC 是默认编程执行者，适合有明确文件/接口/验收要求的实现、测试和重构任务。
- Codex 可直接完成短小、低风险且边界清晰的代码/文档修正及快速测试；跨模块、冻结接口、涉及正式评测或测试矩阵较大的任务，执行工作应明确拆分，最终由 Codex 中枢独立复核。
- DSH 适合可重复的批量或机械处理，必须保留输入、脚本、输出清单及抽查证据。
- 任何执行者不得越权调用模型、读取/输出密钥、覆盖历史结果、切换正式版本或扩大任务授权。

## 3. 保持计划和架构不漂移

实现前写出“本次行为变化如何服务当前阶段目标”，并列出不变量，例如冻结契约、Schema、prompt hash、权限边界、预算、数据版本或回滚目标。

每个里程碑检查：

- 当前改动是否仍解决原任务，而非被测试便利、模型偶然行为或局部修复牵引到新方向？
- 是否改变已冻结接口、架构组成、数据来源、评分标准或授权范围？若是，先记录决策并评估上下游迁移。
- 是否重复修补同一类缺陷？若是，暂停打补丁，回到根因、边界和测试判别力，避免进入修复循环或死角。
- 是否有更上游的结构问题使当前工作失效？若是，记录证据和选择，不继续堆积下游 workaround。

## 4. 实现与验证节奏

1. 记录基线：运行与改动直接相关的测试，确认已有失败、环境问题和版本信息。
2. 做最小改动：不夹带重构，不顺手修改邻近模块；新策略或协议应版本化，旧证据保持只读。
3. 先跑专项测试，再跑受影响模块，最后跑仓库要求的全量检查。复杂任务按里程碑同步，不等整项任务结束才留记录。
4. 测试至少覆盖一个正常路径和一个拒绝/失败路径；关键优先级、权限、预算和安全不变量要有反向测试，能在实现错误时实际失败。
5. 区分测试通过、skip、未运行、环境阻塞和真实外部效果。只报告实际运行的命令、解释器版本、平台和退出结果；mock/离线测试不能被描述为真实模型或端到端效果。
6. 涉及冻结文件或正式记录时，比较改动前后的 hash 和提交差异。LLM 评测还须核对模型输入不含标签/私有真值，原始响应遵守忽略规则和批准的留存边界。

## 5. 交接与独立审查

前序 Agent 产物按 [`handoff-review-protocol.md`](handoff-review-protocol.md) 执行三层检查。中枢审查的最小证据包：

- 分支、HEAD、工作区状态、提交与目标基线关系；
- 修改文件及关键差异，而非仅一段总结；
- 核心测试实际重跑结果，至少一个正常和一个拒绝/失败案例；
- 版本、hash、权限、预算、数据/输出隔离等不变量；
- 已知限制、未运行项、skip 原因和下一步明确 gate。

若报告与工作区不一致，工作区和 Git 证据优先；先记录差异，保持 `review`/`blocked`，不把作者的自检当作中枢审查。

## 6. 复杂任务 checkpoint 和对话压缩恢复

跨多个里程碑的工作应在对应 `agent-work/<domain>/<task-id>/checkpoint.md` 更新：目标、当前状态、已完成/未完成、文件、分支/HEAD、确切命令及结果、正常/失败路径、重要不变量、风险、下一步。事实变化追加到 `docs/WORKLOG.md`；状态只在 `PROJECT_STATUS`/`PROJECT_PLAN` 中维护。

对话压缩或换 Agent 后，不依赖摘要作为唯一事实：先从仓库恢复 checkpoint、决策和提交状态，再重跑最小核心验证。摘要可以帮助定位文件，但不能替代核验。

## 7. Git 和锁文件

- 写操作前确认仓库根、分支、工作区和目标文件；提交前 `git diff --check`，只 add 任务文件，提交后核对 HEAD、提交内容和干净状态。
- 锁文件存在时先检查是否有仍在运行的 Git 进程/操作。只有确认是过期锁且有明确任务授权时才删除；不得为了让命令通过而覆盖或删除有效锁。FUSE/同步文件系统问题要记录文件系统环境和可复现步骤，优先回到本机原生仓库处理。
- 不因无法 push 就报告“已 push”；用远端 ref/哈希核实。不要擅自切换到 main、重置、改写他人提交或 cherry-pick 未核对的内容。

## 8. 状态门和完成定义

- `planned`：任务已定义，尚未执行。
- `in_progress`：正在执行；复杂任务要有里程碑 checkpoint。
- `review`：交付待独立审查、提交/固定环境验证未完成，或仍有重要证据限制。
- `blocked`：外部依赖或事实冲突阻止安全继续；记录具体解除条件。
- `done`：必要检查通过，中枢审查通过，交付已合并到 `main`，状态/日志/下一步已同步。
- `deferred`：明确决定暂缓，记录恢复条件。

代码候选通过不等于生产激活；生产激活不等于真实效果通过；真实评测必须有独立批次、明确范围和授权。每一道 gate 都以文档证据和实际仓库状态为准。

## 9. 结束前检查

```text
[ ] 当前仓库、分支、HEAD 和工作区已核实
[ ] 修改仍符合 PROJECT_STATUS / PROJECT_PLAN / DECISIONS 和任务授权
[ ] 专项及所需回归已运行；skip、失败和未运行项如实区分
[ ] 至少一个正常路径和一个拒绝/失败路径已验证
[ ] 冻结接口、hash、数据和安全边界已检查
[ ] checkpoint、状态页和追加式 WORKLOG 已更新
[ ] commit / push / merge 状态如实核实；阻塞有记录
[ ] 明确写出下一步及其前置条件，不提前跨过下一道 gate
```
