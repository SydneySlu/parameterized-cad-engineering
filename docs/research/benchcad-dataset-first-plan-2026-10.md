# BenchCAD 2.0 数据集优先的项目利用计划

- 日期：2026-10-29
- 任务：DATA-002 planning checkpoint
- 状态：建议方案，待用户/导师确认后冻结范围
- 前提：导师建议尽量直接使用经过审核的开源 CAD 零件族；垂直行业选择不再是首期前置条件

## 1. 计划目标

首期工作从“为一个行业从零定义一个零件族”调整为“围绕 BenchCAD 2.0 已有参数化零件族建立并评测轻量 CAD 生成流程”。项目不把新造一个垂直零件族作为主要工作量，而是尽可能复用 BenchCAD 的构造函数、参数来源、约束和可复现样本生成方式，在其上补充本项目需要的自然语言任务、统一数据格式、Typed CAD IR 适配、检索和验证对照。

研究问题可以表述为：

> 给定 BenchCAD 已审查零件族的参数化规格，LLM 能否把用户的自然语言需求转成来源清楚、满足约束的参数对象；统一适配层、少样本检索和几何验证分别对成功率有何贡献？

这样项目可以横跨多个不同工程零件族，而不声称已经解决某个行业的通用 CAD 设计。主要成果落在数据适配、参数化生成闭环、可复现实验与失败分析。

## 2. 数据和证据边界

BenchCAD 2.0 的资产按以下方式使用：

| 资产 | 计划用途 | 边界 |
|---|---|---|
| GitHub `benchcad-2` 中的 `designs/<family>` 源文件 | 主体数据来源；读取 `part.py`、`spec.py`、`family.json`，复用或调用确定性构造器 | 固定具体 commit；保留 MIT 署名、族来源、审核/验证状态；不能把参数定义与项目自有标注混为一谈 |
| BenchCAD 生成器和校验工具 | 生成合法参数实例、复用参数采样和 CAD 校验方法 | 版本、CadQuery 依赖和运行命令要固定；项目再增加自身 IR、STEP 和端到端检查 |
| BenchCAD 公开生成数据制品 | 如果有可访问的正式发布版本，在核实数据卡后用作既有实例/参考样本 | 不默认 GitHub 中有一个已发行的完整实例集；数据制品按其独立许可证及归属要求处理 |
| BenchCAD 2.0 Public/Core | 官方独立评测、任务格式与错误分类参考 | 当前数据卡禁止训练、微调、蒸馏、RL 环境、检索/搜索语料和再发布；Core 还需要单独协议，不进入项目训练/检索库 |
| Seek-CAD、CADBench | 补充方法和评测设计背景 | 不与 BenchCAD 样本直接拼接成一个未经许可/字段对齐的混合语料 |

官方状态页在 2026-08-02 标记 4/150 个族已合并、0 个 release-qualified。合并族表示进入 BenchCAD 主仓库并经过相应代码/人工评审流程；release-qualified 是更严格的发布阶段。实施时必须重新读取状态页和固定 commit，再确认具体族当前阶段。不要将 150 的项目目标写成 150 个现成族，也不要将 4 个 merged 自动称为正式 released dataset。

已合并的四个族可提供有差异的测试面：

1. `slotted_din_rail`：长尺寸、重复槽、槽数/槽距耦合；
2. `speaker_pole_mount_socket`：圆柱插孔、圆形法兰、四孔布局；
3. `set_screw_shaft_collar`：轴孔、外径、径向紧定螺钉和尺寸联动；
4. `clevis_fork_head`：销孔、叉臂间隙、螺纹柄和标准目录行耦合。

这四者是结构类型不同的通用工业零件族，不是同一行业的同分布样本。它们适合用于跨族接口验证与分族对照，不足以证明开放域 CAD 泛化。

## 3. 推荐的项目结构

保留共同流程，但将零件族差异封装在 family adapter 中：

```text
自然语言/显式参数
        ↓
族路由与任务解析
        ↓
对应族的参数 Schema + 来源/缺失标记
        ↓
项目 Typed CAD IR（族 ID、字段、单位、特征/参数依赖、来源）
        ↓
BenchCAD family adapter
        ↓
原有 BenchCAD 确定性 build() + 项目验证包装
        ↓
STEP/渲染/校验报告
```

关键选择：先**调用经审查的原生 `build()`，不要把四个几何构造器重写一遍，也不要让 LLM 自由生成 CadQuery 代码**。项目 IR 作为统一的结构化意图和执行记录层；family adapter 负责将 IR 参数名映射为对应 `build()` 的具名参数、调用 `check/refine` 或只读验证接口，并记录 builder 的源 commit 和版本。

如果某个族的官方 `refine()` 会采样随机参数，它不能被用来覆盖用户明确给出的值。适配器应区分：

- 用户明确给出的参数；
- 从目录行/标准表可唯一推导的耦合参数；
- 仅用于生成合成测试样本的随机采样参数。

这些来源都写入 manifest/IR；随机 sampler 仅负责离线构造测试实例，不参与真实交互推断。

## 4. 数据准备：不从零做大规模 CAD 清洗

### 4.1 族级审计

逐族锁定以下材料：

- Git commit、族状态、目录结构和许可证；
- `build()` 的参数列表及 `PARAM_SPEC` 一一对应关系；
- 单位、范围、离散 choices、目录 coverage；
- `check()` 的约束条件、失败文案和来源；
- `refine()` 的依赖、随机性和能否用于显式输入路径；
- 输出实体数、构造成功率、STEP 导出/回读和渲染证据。

每族生成一个短的项目侧审核记录。BenchCAD 的验证通过不能替代项目侧验证，但能减少从零清洗和重画 CAD 的工作。

### 4.2 参数实例集

每个族用官方 sampler 生成合法实例，优先保留离散目录规格、参数空间边界和有代表性的特征组合。建议首轮规模：

- 每族 50–100 个合法实例用于覆盖、检索和回归；
- 四族总计 200–400 个实例；
- 每族另抽 10–20 个极值/边界实例做人审和几何检查。

这些数是项目起始预算，不是 BenchCAD 的官方配额。相同参数或几何重复实例应去重，按 family、源型号/目录行和 near-duplicate group 划分开发/测试集合。生成大量随机样本本身不能代替独立测试。

### 4.3 自然语言任务集

参数化族通常没有覆盖我们交互流程的自然语言任务，所以这部分需要补充，但不需大量造 CAD：

- 每族先编写 15–25 个完整规格请求；
- 每族编写 5–10 个缺关键参数、需要追问的请求；
- 每族编写 5–10 个参数冲突或越界请求；
- 总计约 100–180 条任务，保留请求、期望字段、来源、是否追问、约束结果和人工审核状态。

自然语言可从参数规格模板化生成，但测试集的表达方式要经过人工改写/检查，避免每个任务都只是字段名替换，从而高估系统表现。不要把合成输入标成真实用户日志。

## 5. 最小实验设计

同一批固定请求、同一族构造器、同一验证器下比较：

| 条件 | 参数识别方式 | 用来回答的问题 |
|---|---|---|
| A. Oracle 参数 | 直接给正确参数 JSON | 构造器/验证器本身能否稳定生成；作为系统上限 |
| B. LLM + Schema | 提示词给参数定义、单位、约束和 JSON 结构，不提供检索实例 | 单靠结构化提示的抽取表现 |
| C. LLM + Schema + 检索 | 增加同族已验证实例及来源说明 | 小样本检索是否改善字段抽取和合法率 |
| D. 跨族压力测试（可选） | 用其余族的例子或陌生表达，仍使用目标族 Schema | 区分族路由、术语迁移与同族参数抽取能力 |

首期不需要用 Public/Core 样本训练，也不需要 QLoRA/RL。实验的工作量来自多族 adapter、可复现数据切分、请求/追问/冲突任务集，以及严格的端到端评估。

### 核心指标

- 族识别准确率（只有系统支持自动选族时统计）；
- 显式参数字段准确率/精确率/召回率；
- 单位归一化准确率；
- 应追问样本上的追问召回率，以及不应追问样本上的误追问率；
- Schema 通过率、族约束通过率；
- CadQuery 构造成功率、有效实体率、STEP 回读成功率；
- 关键几何量（包围盒、孔中心/孔距、槽数、法兰尺寸）与目标参数的一致率；
- 修复前后通过率、平均重试次数和失败类型；
- A/B/C 三种条件的差值和每族单独结果。

总平均分必须和逐族结果一起报告。四个族不能被当成同一种分布；如果某族失败被其他较简单族掩盖，aggregate 会误导结论。

## 6. 12 周建议计划

| 周期 | 工作 | 阶段交付/决策门 |
|---|---|---|
| 第 1–2 周 | 固定 BenchCAD 源 commit；核对族状态、许可、运行环境；对现有族跑通官方 validate/preview；选择首轮 2 族并确认是否纳入其余族 | 数据清单、许可清单、族审核报告；至少两个不同结构的族端到端可构造 |
| 第 3–4 周 | 建项目 manifest；实现 family adapter；定义足以表达各族参数、单位、来源、约束和特征的 Typed CAD IR v0 | 不改官方族代码即可由项目 IR 调用原生构造器；项目侧验证通过 |
| 第 5–6 周 | 生成和去重参数实例；建立族内分组切分；编写并人工检查自然语言完整/缺失/冲突任务 | 固定 benchmark v0 和可重放样本；完成一族端到端演示 |
| 第 7–8 周 | 接入 LLM JSON 输出；实现参数映射、缺失项追问和约束错误解释；做无检索基线 | LLM + Schema 基线结果；失败案例分类 |
| 第 9–10 周 | 加入同族小样本检索；完成 A/B/C 对照、逐族分析和修复循环对照 | 检索收益和副作用数据；跨族压力测试可选 |
| 第 11–12 周 | 复现实验、修复阻塞问题、整理代码/样本许可/报告/演示 | 公开可复现交付；准确描述使用了哪些 BenchCAD 族及其状态 |

决策门：第 2 周若多个族环境、许可证或适配失败，不要降低验证标准；先缩到两个已通过检查且差异明显的族。第 6 周若数据任务集未锁定，暂停模型调优，优先保证可重复评测。

## 7. “工作量”和项目认可度怎么体现

本项目的工作量不靠从零画大量零件体现，而由可核查的增量组成：

1. 将多个经审核的 BenchCAD 零件族接入同一系统，并保留来源和版本；
2. 定义跨族 manifest 与 Typed CAD IR 到原生构造器的可复现适配层；
3. 建立可审计的自然语言参数任务集，覆盖明确输入、缺失信息、冲突和越界；
4. 通过 Oracle、无检索 LLM、有检索 LLM 的对照实验量化各层贡献；
5. 对各族进行几何、STEP、参数和约束验证，并报告失败类别与限制。

这是“在验证数据集基础上做系统研究”，不是把数据集本身称作项目贡献，也不是声称新训练了 CAD 基础模型。

## 8. 风险和控制

| 风险 | 控制 |
|---|---|
| 将 150 目标误写成现有 150 族 | 以固定 commit 和状态页逐族记账；报告实际使用数量和状态 |
| merged 被误写为 release-qualified | 明确记录各族状态；优先用正式 versioned release，若没有则清楚标注来自主仓库的族源码 |
| 族之间参数不统一，强行做“通用 IR” | IR 只统一公共信封和 provenance；参数字段/构造特征由 family adapter 保留族特异性 |
| 随机采样实例泄漏进测试 | 按目录行、特征组合和几何近重复组切分；固定 seed 和 manifest |
| 合成自然语言过于模板化 | 留出人工改写测试表达；报告合成来源，不伪装为真实用户数据 |
| 检索样例与测试参数近重复 | 以规格行/参数邻域分组，检索库和测试集在组级隔离 |
| Public/Core 用途越界 | 只走官方允许的 evaluation 流程；不放入项目 retrieval/training 数据目录 |
| 多族范围过大 | 先两个族跑通闭环，之后按相同接口扩展到四族；范围由第 2 周和第 6 周门控 |

## 9. 建议给导师确认的最终范围

建议汇报并请导师确认以下具体口径：

> 项目以 BenchCAD 2.0 社区参数化零件族为主数据源，首轮选两个结构差异明显且当前状态/许可证/构造验证可确认的族，架构设计为可扩展到当前全部可用族；完成项目 IR/适配器、自然语言参数任务集、检索对照和几何验证。若进度允许，扩到四个已合并族；新增零件族只作为补充，不做首期前置。BenchCAD Public/Core 保持官方评测用途，不进入检索或训练语料。

该范围保留数据集优先和多族利用，同时给 12 周留出可控的最小交付路径。
